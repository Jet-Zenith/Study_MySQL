## 为什么需要undo log？

**undo log** 直译过来就是“撤销日志”。你可以把它当成平时写文档、写代码时狂按的 **`Ctrl + Z` (撤销键)** 。只要你对数据库里的数据进行了“增、删、改”，MySQL 就会悄悄把**相反的动作**记在这个小本本上。

<img src="../images/image-20260317145031507.png" alt="image-20260317145031507" style="zoom:80%;" />

### 1. 绝技一：保障事务的原子性（吃后悔药）

- **大白话翻译**：原子性就是“要么全做完，要么全当没发生过”。
- **实战场景**： 假设你在执行一个大事务：先给张三扣 100 块，再给李四加 100 块。 当你刚把张三的钱扣完，突然网断了，或者程序报错了！这个时候事务执行失败，必须**手动 回滚 (Rollback)**。
- **undo log 怎么救场？**： 在你扣张三钱之前，MySQL 已经在 undo log 里写下了一句话：“张三原来的钱是 500”。 当系统报错需要回滚时，MySQL 就会翻开这个日记本，执行**逆向操作**：把张三的钱重新加回 500。一切恢复如初，完美保障了原子性。

### 2. 绝技二：实现 MVCC（看历史老照片）

- **大白话翻译**：MVCC 就是多版本并发控制。你可以把它理解为数据库里的 **Git 版本控制系统**。
- **实战场景**： 你正在疯狂修改某一行数据（比如把价格从 10 块改成 20 块），但你**还没有点击提交 (Commit)**。 这个时候，有个顾客跑来查这个商品的价格。
- **undo log 怎么救场？**： 为了不让顾客看到你改了一半的“脏数据”（20块），MySQL 会顺着这行数据上隐藏的指针，直接去 **undo log** 里翻出这行数据在修改前的**历史版本**（10块） 。 结果就是：你改你的最新版，顾客读他的历史版。大家互不干扰，数据库的并发读取速度飞起！

------

**一句话总结 undo log：** 它就是一个专门记录“数据修改前是什么样”的后悔药本子。一是为了在报错时能**把数据恢复原样**（原子性），二是为了在别人并发查询时能**给别人看旧数据**（MVCC）。



## 为什么需要 Buffer Pool？

内存的速度是磁盘的十万倍。如果每次执行 `SELECT` 都要去磁盘里现捞数据，每次 `UPDATE` 都要直接写回磁盘，那数据库慢得连并发 100 都能把系统卡死

于是Innodb 存储引擎设计了一个**缓冲池（Buffer Pool）**，来提高数据库的读写性能。

- **读的优化**：当你要查一条数据时，InnoDB 会把那一整页（16KB）的数据全部搬到工作台（Buffer Pool）上。下次你再查同一页的其他数据，直接从内存拿，**这就是“缓存命中”，速度是纳秒级的。**

- **写的优化**：当你要改数据时，InnoDB 会直接在工作台（Buffer Pool）上把数据改掉。改完之后，它不管了，直接给客户端返回“修改成功”。（至于怎么保证断电不丢数据，那是我们下节要讲的 redo log 的活儿）。这些被改过但还没同步回磁盘的页，被称为**“脏页 (Dirty Page)”**。

<img src="../images/image-20260317151001341.png" alt="image-20260317151001341" style="zoom:80%;" />

### Buffer Pool 缓存什么？

InnoDB 会把存储的数据划分为若干个「页」，以页作为磁盘和内存交互的基本单位。因此，Buffer Pool 同样需要按「页」来划分。

在 MySQL 启动的时候，**InnoDB 会为 Buffer Pool 申请一片连续的内存空间，然后按照默认的`16KB`的大小划分出一个个的页， Buffer Pool 中的页就叫做缓存页**。

![image-20260317151604329](../images/image-20260317151604329.png)

在这个庞大的内存池子里，主要缓存了以下这几大块核心内容：

1. **数据页 (Data Pages)**：这是占地面积最大的。里面装的就是你们表里实打实的行记录。
2. **索引页 (Index Pages)**：我们之前画过的 B+ 树的各个节点（尤其是根节点和非叶子节点），为了保证找寻极快，通常都会常驻在 Buffer Pool 里。
3. **Undo 页 (Undo Pages)**：这就跟我们上一层楼彻底闭环了！你每次修改数据产生的“后悔药（撤销记录）”，就是被写在这个区域里的。
4. **锁信息 (Lock Info)**：我们之前聊得热火朝天的行锁、间隙锁、临键锁，它们其实都是内存中的数据结构，平时就暂存在 Buffer Pool 里。
5. **插入缓冲 (Change Buffer)**：这是一个极其高阶的性能优化组件。当你往非唯一索引里插入数据时，为了避免频繁读写随机的磁盘索引页，MySQL 会先把插入动作“暂存”在这个池子里，等合适的时机再合并。
6. **自适应哈希索引 (Adaptive Hash Index)**：InnoDB 自己会在后台偷偷观察你，如果发现你频繁地用同一个条件查询某一行数据，它会在 Buffer Pool 里为这行数据自动建一个哈希索引，让你下次查询变成 O(1) 的极限速度。

> ### Undo 页是记录什么？

开启事务后，InnoDB 层更新记录前，首先要记录相应的 undo log，如果是更新操作，需要把被更新的列的旧值记下来，如果是更新操作，需要把被更新的列的旧值记下来



> ### 查询一条记录，就只需要缓冲一条记录吗？

不是的，当我们查询一条记录时，InnoDB 是会把整个页的数据加载到 Buffer Pool 中，将页加载到 Buffer Pool 后，再通过页里的「页目录」去定位到某条具体的记录。



## 为什么需要 redo log ？

内存总是不可靠，万一断电重启，还在buffer pool中没来得及落盘的脏页数据就会丢失。

为了防止断电导致数据丢失的问题，当有一条记录需要更新的时候，InnoDB 引擎就会先更新内存（同时标记为脏页），然后将本次对这个页的修改以 redo log 的形式记录下来，**这个时候更新就算完成了**。

后续，InnoDB 引擎会在适当的时候，由后台线程将缓存在 Buffer Pool 的脏页刷新到磁盘里，这就是**WAL （Write-Ahead Logging）技术**。

![image-20260317171558477](../images/image-20260317171558477.png)

> ### 什么是 redo log？

redo log 是物理日志，记录了某个数据页做了什么修改，比如**对 XXX 表空间中的 YYY 数据页 ZZZ 偏移量的地方做了AAA 更新**，每当执行一个事务就会产生这样的一条或者多条物理日志。

在事务提交时，只要先将 redo log 持久化到磁盘即可，可以不需要等到将缓存在 Buffer Pool 里的脏页数据持久化到磁盘。

当系统崩溃时，虽然脏页数据没有持久化，但是 redo log 已经持久化，接着 MySQL 重启后，可以根据 redo log 的内容，将所有数据恢复到最新的状态。



> ### 被修改 Undo 页面，需要记录对应 redo log 吗？

需要。开启事务后，InnoDB 层更新记录前，首先要记录相应的 undo log，如果是更新操作，需要把被更新的列的旧值记下来，也就是要生成一条 undo log，undo log 会写入 Buffer Pool 中的 Undo 页面。

不过，**在内存修改该 Undo 页面后，也是需要记录对应的 redo log，因为undo log也要实现持久性的保护**



> ### redo log 和 undo log 区别在哪？

这两种日志是属于InnoDB存储引擎的日志，它们的区别在于：
redo log记录了此次事务「**修改后**」的数据状态，记录的是**更新之后的值**，主要用于事务崩溃恢复，**保证事务的持久性**。
undo log记录了此次事务「**修改前**」的数据状态，记录的是**更新之前的值**，主要用于事务回滚，**保证事务的原子性**。

事务提交之前发生了崩溃（这里的崩溃不是宕机崩溃，而是事务执行错误），重启后会通过 undo log 回滚事务。

事务提交之后发生了崩溃（这里的崩溃是宕机崩溃），重启后会通过 redo log 恢复事务

![image-20260317173511797](../images/image-20260317173511797.png)

> ### redo log 要写到磁盘，数据也要写磁盘，为什么要多此一举？

写入 redo log 的方式使用了追加操作， 所以磁盘操作是**顺序写**；

而写入数据需要先找到写入位置，然后才写到磁盘，所以磁盘操作是**随机写**。磁盘的「顺序写 」比「随机写」 高效的多。

可以说这是 WAL 技术的另外一个优点：**MySQL 的写操作从磁盘的「随机写」变成了「顺序写」**



> ### 为什么需要 redo log 

- **实现事务的持久性，让 MySQL 有 crash-safe（崩溃恢复） 的能力**，能够保证 MySQL 在任何时间段突然崩溃，重启后之前已提交的记录都不会丢失；

- **将写操作从「随机写」变成了「顺序写」**，提升 MySQL 写入磁盘的性能。



> ### 产生的 redo log 是直接写入磁盘的吗？

产生的 redo log 是先写到 MySQL 的内存 Buffer 里，再写到操作系统的内存 Cache 里，最后才被强制刷入物理磁盘的



### redo log 什么时候刷盘？

#### 1. 不受控制的自动刷盘

1. **后台线程的“滴答”定时器（每秒一次）**
   - InnoDB 内部有一个极其勤奋的后台线程，它就像打点计时器一样，**大约每隔 1 秒钟**，就会主动把内存（redo log buffer）里的日志强行刷进物理磁盘。
   - **注意**：这个动作是无差别的，哪怕你的事务**还没有提交**，它产生的 redo log 也有可能被这个后台线程顺手给刷进磁盘里！
2. **Redo Log Buffer 空间快不够用了（占用达到一半）**
   - MySQL 给 redo log 分配的内存（buffer）是有限的（默认 16MB）。
   - 如果你在执行一个极其巨大的事务（比如疯狂 `UPDATE` 一百万行数据），日志瞬间暴增。当内存里的日志量达到了 Buffer 总空间的一半（比如 8MB）时，MySQL 会产生危机感，不等你提交，它会主动把这些日志提前刷进磁盘腾地方。
3. **MySQL 正常关机时**
   - 当你执行命令正常停止 MySQL 服务时，系统肯定要“打扫战场”，把所有停留在内存里的 redo log 全部安全地刷入磁盘，然后才会正式闭眼。

#### 2. 受你控制的主动刷盘

这是最核心的时机，由 MySQL 的参数 `innodb_flush_log_at_trx_commit` 来决定。当你敲下 `COMMIT` 提交事务的那一刻，系统会根据你设置的策略来行动：

- **参数1（默认值，绝对安全）：每次提交，立刻刷盘**
  - **时机**：只要你一提交事务，MySQL 必须眼睁睁看着这段 redo log 真正写进物理磁盘，才算你提交成功。
  - **效果**：数据绝对不会丢，但每次提交都要等磁盘转一圈，性能最受影响。
- **参数0（极度奔放，性能最高）：提交归提交，我不刷盘**
  - **时机**：你提交事务时，MySQL 只把日志留在自己的内存里（redo log buffer），根本不碰磁盘。
  - **效果**：提交速度快得飞起！但全靠后台线程每秒去刷一次盘，如果系统突然崩溃，会丢失最近 1 秒的数据。
- **参数2（中庸之道，大厂最爱）：提交时只交到系统手里**
  - **时机**：你提交事务时，MySQL 把日志交给了操作系统的内存（Page Cache），然后就不管了，系统会负责后续真正的刷盘（通常也是 1 秒左右刷一次）。
  - **效果**：性能很好。只要服务器不断电，单纯 MySQL 进程崩溃是不会丢数据的；但如果机房整体停电，依然会丢 1 秒的数据。



> ### 这三个参数的应用场景是什么？

这三个参数的数据安全性和写入性能的比较如下：

- 数据安全性：参数 1 > 参数 2 > 参数 0
- 写入性能：参数 0 > 参数 2> 参数 1

所以，数据安全性和写入性能是熊掌不可得兼的，**要不追求数据安全性，牺牲性能；要不追求性能，牺牲数据安全性**。



### redo log 文件(位于磁盘)写满了怎么办？

默认情况下， InnoDB 存储引擎有 1 个重做日志文件组( redo log Group），由ib_logfile0` 和 `ib_logfile1组成。redo log 是循环写的方式，相当于一个环形，InnoDB 用 write pos 表示 redo log 当前记录写到的位置，用 checkpoint 表示当前要擦除的位置

<img src="../images/image-20260318133146877.png" alt="image-20260318133146877" style="zoom:80%;" />

- write pos 和 checkpoint 的移动都是顺时针方向；

- write pos ～ checkpoint 之间的部分（图中的红色部分），用来记录新的更新操作；

- check point ～ write pos 之间的部分（图中蓝色部分）：待落盘的脏数据页记录；

如果 write pos 追上了 checkpoint

①MySQL 会立刻挂起所有新的更新、插入和删除操作 

②系统会强行催促后台线程将 Buffer Pool 中的脏页刷新到磁盘中，擦除旧的redo log记录

③等擦除完旧记录腾出了空间，checkpoint 就会顺时针移动，MySQL恢复正常运转



PS：内存不是随便乱用的，操作系统为了安全，把内存劈成了两半：用户空间和内核空间

| **概念**            | **物理位置**     | **属于谁**  | **核心作用**                        |
| ------------------- | ---------------- | ----------- | ----------------------------------- |
| **Buffer Pool**     | 内存（用户空间） | MySQL申请的 | 缓存数据和索引（超级工作台）        |
| **Redo Log Buffer** | 内存（用户空间） | MySQL申请的 | 暂存刚生成的 redo log               |
| **Page Cache**      | 内存（内核空间） | 操作系统    | 暂存准备写入硬盘的文件数据          |
| **Redo Log Group**  | 物理磁盘         | 磁盘文件    | 环形文件组，redo log 的最终物理归宿 |



## 为什么需要 binlog ？

binlog 文件是记录了所有数据库表结构变更和表数据修改的日志，不会记录查询类的操作

MySQL 在完成一条更新操作后，Server 层还会生成一条 binlog，等之后事务提交的时候，会将该事物执行过程中产生的所有 binlog 统一写 入 binlog 文件。

> ### 为什么有了 binlog， 还要有 redo log？

核心原因就藏在它们的**“归属权”**里：

- **redo log** 是 **InnoDB 存储引擎** 自己部门私有的。如果你的表用的是 MyISAM 引擎，那是完全没有 redo log 的。
- **binlog** 则是位于更上层的 **MySQL Server 层** 拥有的。不管底下用的是 InnoDB 还是 MyISAM，只要你对数据库里的数据进行了**修改（增、删、改、建表等）**，Server 层都会统统把这些操作记录到 binlog 里。



### redo log 和 binlog 有什么区别？

| **对比维度** | **redo log 重做日志**                                        | **binlog 归档日志**                                          |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **适用对象** | Innodb 存储引擎实现的日志                                    | Server 层实现的日志，所有存储引擎都可以使用                  |
| **日志格式** | 物理日志（数据页的修改），比如：“在第 5 号数据页的偏移量 100 处，把数字 0 改成了 1”。 | 逻辑日志（SQL 语句或行数据变化），比如：“给 `user` 表里 `id=2` 的那行数据，执行了一句 `UPDATE` 把年龄改成了 18 岁”。 |
| **写入方式** | 空间固定，循环写（会覆盖历史）                               | 追加写（无限生成新文件）                                     |
| **核心用途** | 崩溃、掉电等故障恢复                                         | 数据备份、删库恢复、主从复制                                 |



> ### 如果不小心整个数据库的数据被删除了，能使用 redo log 文件恢复数据吗？

不可以使用 redo log 文件恢复，只能使用 binlog 文件恢复。

binlog 文件保存的是全量的日志，也就是保存了所有数据变更的情况，理论上只要记录在 binlog 上的数据，都可以恢复



### 主从复制是怎么实现？

单台 MySQL 根本扛不住成千上万的并发读写。所以通常会搞“读写分离“。在写数据时只写主库，在读数据时只读从库，这样即使写请求会锁表或者锁记录，也不会影响读请求的执行。

<img src="../images/image-20260318153126808.png" alt="image-20260318153126808" style="zoom:80%;" />

**主库（Master）专门负责写数据，多个从库（Slave）专门负责给用户读数据。**主库和从库是两个**物理间隔很远**的服务器

MySQL 集群的主从复制过程梳理成 3 个阶段：

- **写入 Binlog**：主库写 binlog 日志，提交事务，并更新本地存储数据。

- **同步 Binlog**：把 binlog 复制到所有从库上，每个从库把 binlog 写到暂存日志中。

- **回放 Binlog**：回放 binlog，并更新存储引擎中的数据。

![image-20260318152613624](../images/image-20260318152613624.png)

#### 第一棒：主库的 `Log Dump` 线程（总部的广播员）

- **动作**：当你在主库上完成了一次数据修改（比如插入了一条新用户），主库会把这个动作记录在自己**本地**的 `binlog` 里。
- **交接**：此时，主库里的 **Log Dump 线程** 就像一个广播员，只要看到 `binlog` 有更新，它就会立刻把这段最新的日志，通过 **TCP/IP** 网络发送给远在天边的从库。

#### 第二棒：从库的 `I/O` 线程（分公司的速记员）

- **动作**：从库里面有一个专门负责盯梢的 **I/O 线程**。它和主库建立了长连接，死死盯着主库的动静。
- **交接**：当它接收到主库发来的 `binlog` 数据后，它**并不会立刻去修改从库的数据**（因为直接改数据太慢了，容易造成网络拥堵）。它会以极快的速度，把接收到的内容写到从库**本地**的一个临时日志文件里。这个临时文件，叫做 **中继日志 (`relay log`)**。
- **状态**：到这一步，相当于分公司的速记员把总部的最新文件抄在了本地的记事本上。

#### 第三棒：从库的 `SQL` 线程（分公司的执行长）

- **动作**：从库里还有另一个苦力线程，叫做 **SQL 线程**。它的眼睛死死盯着刚才那个记事本（`relay log`）。
- **交接**：只要发现 `relay log` 里多出了新的内容，它就会立刻把里面的操作翻译出来（比如发现是一句 `INSERT` 语句），然后在从库自己的数据库里**原原本本地重放（Replay）一遍**。
- **结果**：因为从库执行了和主库一模一样的操作，所以从库的数据也就和主库保持了绝对的一致！

> 1.**在北京（主库端）**：你在北京的主库上执行了 `UPDATE`，主库把这件事写进了**北京本地硬盘**的 `binlog` 里。
>
> 2.**在连接着京沪的网线上（跨机器传输）**：北京主库里的 `Log Dump 线程`，通过 **TCP/IP 网络**，把这段 `binlog` 的内容打包，像发微信一样发送给上海的从库。
>
> 3.**在上海（从库端）**：上海从库里的 `I/O 线程` 接收到网络包，先赶紧存到**上海本地硬盘**的 `relay log` 里。然后上海从库的 `SQL 线程` 看着这个 `relay log`，在**上海本地的数据库**里再执行一遍那个 `UPDATE`。





> ### 从库是不是越多越好？

**从库绝对不是越多越好！** 主库上的每一个从库，都会在主库端独占一个 `Log Dump` 线程。如果你挂了 10 个从库，主库就要拉起 10 个线程，把同一份 binlog 数据通过网络分别发送 10 次。如果从库挂得太多，反而会直接把你的主库给**“拖死”**。

所以在实际使用中，一个主库一般跟 2～3 个从库



> ### MySQL 主从复制还有哪些模型？

#### 1. 异步复制  —— “发完我就走”

- **操作**：主库（老板）在群里发了一条通知（binlog），发完之后**瞬间就把手机揣兜里了，直接告诉客户“搞定了”**。他根本不管底下的从库（员工）到底收没收到、网卡没卡。
- **优点**：极其丝滑，主库性能天下无敌。
- **致命痛点**：就像截图里说的，一旦主库突然死机，而刚才那条通知因为网络延迟还没传到从库那里，那这条数据就**彻底丢失**了。

#### 2. 同步复制  —— “所有人必须回复收到”

- **操作**：主库发完通知后必须等到所有的从库全都回复了“收到”，才对客户说“搞定了”。
- **优点**：数据绝对安全，不管死哪台机器都不怕。
- **致命痛点**：只要有一个从库网络卡了或者宕机了，整个主库就会被死死卡住，完全失去响应。在真实的互联网高并发场景下，这简直是自杀。

#### 3. 半同步复制  —— “只要有一个人理我就行”

- **操作**：**折中方案**。主库发完通知后，只要底下有哪怕一个从库回复了“收到”（从库把 binlog 写进自己的 relay log 了），主库就立刻给客户返回成功。
- **优点**：完美兼顾了性能和数据安全。就算主库立刻原地爆炸，至少那个回复了“收到”的从库身上有最新的数据，拉出来接管业务就行了，不会丢数据。



### binlog 什么时候刷盘？

事务执行过程中，先把日志写到 binlog cache（Server 层的 cache），事务提交的时候，再把 binlog cache 写到 binlog 文件中。

> ### 什么时候 binlog cache 会写到 binlog 文件？

<img src="../images/image-20260318162119166.png" alt="image-20260318162119166" style="zoom:80%;" />

MySQL提供一个sync_binlog参数来控制数据库的binlog刷到磁盘上的频率:

- sync_binlog=0的时候，表示每次提交事务都只write，不fsync，后续交由操作系统决定何时将数据持久化到磁盘;
- sync_binlog=1的时候，表示每次提交事务都会write，然后马上执行fsync;
- sync_binlog=N(N>1)的时候，表示每次提交事务都write，但累积N个事务后才fsync。



> ### 先小结下update 语句的执行过程。

当优化器分析出成本最小的执行计划后，执行器就按照执行计划开始进行更新操作。

具体更新一条记录 `UPDATE t_user SET name = 'xiaolin' WHERE id = 1;`的流程如下:

#### 一、准备阶段

- **1. 找数据（Server 层执行器发话）**：执行器跑去问 InnoDB（底层仓库）要 `id=1` 的数据。
- **2. 搬到工作台（Buffer Pool 发力）**：InnoDB 先看一眼自己的豪华工作台（**Buffer Pool**）。
  - 如果在桌上，直接拿来用（内存命中）。
  - 如果不在，就得老老实实去底层物理磁盘里，把那一整页（16KB）的数据“搬”到 Buffer Pool 里。
- **3. 对比查验**：执行器拿到数据一看
  - 如果原来的名字已经是 'xiaolin' 了，那就直接下班，啥也不干。
  - 如果不是，那就把新旧数据都交给 InnoDB，让它开始干活。

#### 二、核心执行阶段

- **第一棒：生成 undo log**
  - 在真正动手改数据之前，InnoDB 必须先给自己留条后路。
  - 它会在 Buffer Pool 的 **Undo 页**里写下一笔：“原来的名字叫 xxx”。万一等会儿出错或者事务被Rollback，就能靠它恢复原样。
  - 因为修改了 Undo 页本身，这个修改动作也会触发生成一条 **redo log**！这就是咱们之前说的“老大哥保护小弟”。
- **第二棒：生成 redo log**
  - 后路留好了，InnoDB 开始在 Buffer Pool 里把名字真正改成了 'xiaolin'。同时标记**“脏页”**。
  - 为了防止突然停电导致脏页丢失，InnoDB 立刻把这次修改动作写进了 **redo log buffer** 里，后续再刷进磁盘
  - 这就是 **WAL（Write-Ahead Logging）技术**：数据可以等会儿再刷入磁盘，但日志必须先写好。
- **第三棒：生成 binlog**
  - 至此，一条记录更新完了。然后上层的 MySQL Server 层开始记录该语句对应的 binlog，记入binlog cache：“某年某月某日，把 id=1 的名字改成了 xiaolin”。但并没有刷新到硬盘上的 binlog 文件，在事务提交时才会统一将该事务运行过程中的所有 binlog 刷新到硬盘。

#### 三、悬念阶段

到目前为止，这条 `UPDATE` 语句其实**已经执行完了**。

只有当客户端真正敲下 `COMMIT`的那一瞬间，系统才会根据设置的刷盘参数（比如 `sync_binlog` 和 `innodb_flush_log_at_trx_commit`），把这两个日志刻录到物理硬盘上。



## 为什么需要两阶段提交？

事务提交后，redo log 和 binlog 都要持久化到磁盘，但是这两个是独立的逻辑，可能出现半成功的状态，这样就造成两份日志之间的逻辑不一致。

- 如果先写成功了 redo log，突然断电，binlog 没写成功。MySQL重启后主库恢复了数据，但从库没收到日志，主从数据不一致！

- 如果先写成功了 binlog，突然断电，redo log 没写成功。从库跟着改了数据，但主库自己重启后这个事务无效，依然不一致！

两阶段提交的唯一目的，就是为了把这俩性格迥异的日志**强行“锁死”在一起，实现原子性**：要么他俩一起写成功，要么他俩一起作废。



### 两阶段提交的过程是怎样的？

我们把 InnoDB 引擎（管 redo log 的）想象成**“底层金库的保管员”**，把 MySQL Server 层（管 binlog 的）想象成**“上层的广播员”**。

<img src="../images/image-20260319123849946.png" alt="image-20260319123849946" style="zoom:80%;" />

#### 第一阶段：Prepare 阶段

- **执行者**：InnoDB 引擎（金库保管员）。
- **动作**：公司发生一笔交易（MySQL执行一条增删改语句），保管员把内存里修改好的数据所对应的 `redo log`，直接写入物理磁盘。
- **最核心的细节**：写完之后，保管员会在这个 `redo log` 上重重地盖上一个印章——**`prepare`（准备状态）**。
- **潜台词**：“我这边物理记录已经落盘了，随时可以正式提交，但必须等上面广播员（binlog）发出的最终行动指令。”

#### 第二阶段：Commit 阶段

- **动作 1：写 Binlog（广播员发话）**
  - **执行者**：MySQL Server 层。
  - **动作**：Server 层把这次业务修改的逻辑日志，统统写入到 `binlog` 文件，并强制刷入物理磁盘。
  - **潜台词**：“全公司的历史账本已经正式记录了，这笔交易现在是铁板钉钉的事实了！”
- **动作 2：改 Redo Log 状态（保管员最终确认）**
  - **执行者**：InnoDB 引擎。
  - **动作**：当 Server 层确认 binlog 已经稳稳落盘后，就会给底层的InnoDB 保管员发个信号。InnoDB 接到信号，立刻把刚才那个盖着 `prepare` 印章的 `redo log`，划掉，重新盖上一个 **`commit`（提交状态）** 的印章。
  - **潜台词**：“大哥发话了，交易彻底闭环，任务圆满结束！”



### 异常重启会出现什么现象？

在推演崩溃之前，你需要知道一个极其关键的**暗号：XID（事务 ID）**。

<img src="../images/image-20260319125247226.png" alt="image-20260319125247226" style="zoom:80%;" />

####  致命时刻 A：写完 Redo Log (Prepare)，还没写 Binlog 就断电了

- **现场勘探**：服务器重启，InnoDB 引擎层开始巡视自己的地盘（检查 redo log）。它发现了一个带有 **`prepare`（准备）** 印章的事务。
- **搜证逻辑**：InnoDB 不敢自己做主，它拿着这个事务的 XID，跑去 Server 层的 `binlog` 文件里去搜。
- **发现真相**：结果在 `binlog` 里**根本找不到**这个 XID（因为还没来得及写就断电了）。
- **最终判决：回滚 (Rollback)！**
  - **原因**：既然 `binlog` 没写成功，说明从库绝对不可能收到这条更新。为了保证主从库数据绝对一致，主库自己也不能要这条数据了。于是，InnoDB 掏出之前准备好的 `undo log`，把内存里的修改逆向撤销掉。

####  致命时刻 B：写完了 Binlog，还没改 Redo Log (Commit) 就断电了

- **现场勘探**：服务器再次重启，InnoDB 引擎依然发现了一个带有 **`prepare`** 印章的 redo log（因为第三步还没做，印章没来得及换）。
- **搜证逻辑**：InnoDB 再次拿着 XID，跑去 `binlog` 文件里搜。
- **发现真相**：这次，它在 `binlog` 里**找到了**完整无缺的对应记录！
- **最终判决：强制提交 (Commit / Roll-forward)！**
  - **原因**：这正是两阶段提交最精妙的地方！既然 `binlog` 已经完整写进磁盘了，说明这条广播已经确凿无疑地发出去了，从库早晚会拿到并执行它。为了保证主从一致，主库自己**必须**承认这笔交易。于是，InnoDB 不管之前发生了什么，强行把这个 `prepare` 状态的 redo log 补齐，改成 `commit` 状态，让数据真正生效。

---------

所以说，**两阶段提交是以 binlog 写成功为事务提交成功的标识**

因为它把原本“两个互相独立的文件到底听谁的”这个问题，变成了一个**“唯 binlog 马首是瞻”**的绝对真理。只要 binlog 成功了，这事儿就算成了；binlog 没成功，这事儿就算黄了。这就彻底杜绝了主从数据不一致的灾难。



> ### 处于 prepare 阶段的 redo log 加上完整 binlog，重启就提交事务，MySQL 为什么要这么设计?

binlog 已经写入了，之后就会被从库（或者用这个 binlog 恢复出来的库）使用。所以，在主库上也要提交这个事务。采用这个策略，主库和备库的数据就保证了一致性。



> ### 事务没提交的时候，redo log 会被持久化到磁盘吗？

会的。事务执行中间过程的 redo log 也是直接写在 redo log buffer 中的，这些缓存在 redo log buffer 里的 redo log 也会被「后台线程」每隔一秒一起持久化到磁盘。也就是说，**事务没提交的时候，redo log 也是可能被持久化到磁盘的**。但是 binlog 必须在事务提交之后，才可以持久化到磁盘。



### 两阶段提交有什么问题？

**磁盘 I/O 次数高**：对于“双1”配置，每个事务提交都会进行两次 fsync（刷盘），一次是` redo log `刷盘，另一次是 `binlog `刷盘。

**锁竞争激烈**：在两阶段提交的流程基础上，还需要加一个锁来保证提交的原子性，从而保证多事务的情况下，两个日志的提交顺序一致。

> ### 为什么两阶段提交的磁盘 I/O 次数会很高？

`binlog `和 `redo log` 在内存中都对应的缓存空间，`binlog `会缓存在 `binlog cache`，`redo log `会缓存在 `redo log buffer`，它们持久化到磁盘的时机分别由`sync_binlog `和 `innodb_flush_log_at_trx_commit `两个参数控制。一般我们为了避免日志丢失的风险，会将这两个参数设置为1:

- 当 `sync_binlog =1`的时候，表示每次提交事务都会将 `binlog cache` 里的`binlog`直接持久到磁盘；

- 当`innodb_flush_ log_attrx_commit =1`时，表示每次事务提交时都将缓存在`redo log buffer` 里的`redo log`持久化到磁盘

如果两个参数都设置为1，那么在每个事务提交过程中，都会至少调用2次刷盘操作，一次`redo log`刷盘，一次`binlog`落盘，这会成为性能瓶颈。

> ### 为什么锁竞争激烈？

在早期的 MySQL（5.6 版本之前）中，为了保证 `binlog` 里的日志顺序，和 `redo log` 里的事务提交顺序**绝对一致**，MySQL 引入了一把极其沉重的全局大锁，叫做 **`prepare_commit_mutex`**。在一个事务获取到锁时才能进入 `prepare `阶段，一直到 `commit `阶段结束才能释放锁，下个事务才可以继续进行 prepare 操作。通过加锁虽然完美地解决了顺序一致性的问题，但在并发量较大的时候，就会导致对锁的争用，**性能不佳**。



## 组提交

引入了组提交机制后，prepare 阶段不变，只针对 commit 阶段，将 commit 阶段拆分为三个过程：

<img src="../images/image-20260319150238463.png" alt="image-20260319150238463" style="zoom: 50%;" />

### 第一关：Flush 阶段（上车买票，写入缓存）

- **动作**：多个事务排成一个队列进入提交`commit`流程这个阶段。
- **队长发威**：队长获取到队列的锁，然后**代表全队所有人**，把大家暂存在内存里的 binlog 数据，统统写入到操作系统的内存缓存（Page Cache）中。
- **结果**：在这个阶段，数据还没真下硬盘，只是全员打包上车了。

### 第二关：Sync 阶段（发车过收费站，物理刷盘）

- **动作**：队长开着装满所有人 binlog 的大巴车，来到了最耗时的物理磁盘收费站。
- **物理合并**：队长向操作系统发起**仅此一次的 `fsync` 调用**。磁盘“哐当”转一圈，直接把这整整一车人（比如 100 个事务）的 binlog 一次性全部刻录到了物理硬盘上！
- **结果**：原来这 100 个事务需要做 100 次 `fsync`，现在被**浓缩成了 1 次**！磁盘 I/O 压力瞬间被干掉了 99%。

### 第三关：Commit 阶段（下车敲章，完成事务）

- **动作**：既然大哥 binlog 已经全员安全落盘了，现在要去底层 InnoDB 金库改印章状态了。
- **队长收尾**：队长再次代表全队，按照之前排好的顺序，去 InnoDB 引擎层，把全队所有人的 `redo log` 状态，全部从 `prepare` 划掉，盖上最终的 **`commit`** 印章。
- **全员解散**：队长干完所有脏活累活后，唤醒所有在车上睡觉的队员，宣布：“兄弟们，咱们全组的事务都提交成功了，大家可以给客户端返回成功响应了！”

通过把一把“全局大锁”敲碎成三把“阶段小锁”（锁粒度减小），MySQL 让 Flush、Sync、Commit 这三个阶段可以**像工厂流水线一样同时运转（并发执行）**。大家各司其职，互不干扰，从而把数据库的吞吐量推向了极致。



> ### 有 binlog 组提交，那有 redo log 组提交吗？

我们上一节讲的“拼车大巴”，其实全名叫 **Binlog 组提交**。它确实把第二阶段的 `binlog` 刷盘合并了，但是第一阶段的 **`redo log` (prepare 状态)** 呢

#### 1. MySQL 5.6 的“半吊子”优化：各自打车 + 集中坐大巴

- **痛点场景**：在 5.6 版本，虽然 `binlog` 已经拼大巴车了，但最前面的 `prepare` 阶段（刷 `redo log`）依然是极其原始的各自刷盘
- **动作还原**：事务 A、B、C 想要提交。它们必须**各自花钱打一辆出租车（产生 3 次独立的磁盘 I/O）**，先把自己的 `redo log` 刷入磁盘变成 `prepare` 状态。打完车后，它们才来到车站，一起坐上 **Binlog 大巴车（产生 1 次共享的磁盘 I/O）** 完成后续流程。
- **结论**：虽然比以前好多了，但在“双 1 配置”下，磁盘 I/O 次数依然居高不下，因为 `redo log` 没能拼上车。

#### 2. MySQL 5.7 的终极进化：两路人马上同一辆大巴！

核心：**“推迟到组提交的 flush 阶段，也就是说 prepare 阶段融合在了 flush 阶段。”**

MySQL 5.7 决定：**既然大家最后都要上同一辆大巴，为什么不让队长把两份行李（redo log 和 binlog）一起搬上车呢？**

于是，流程被彻底重构了：

- **强行拖延**：事务 A、B、C 执行到 `prepare` 阶段时，**系统绝对不允许它们立刻去刷磁盘**，而是让它们拿着自己的 `redo log` 乖乖去“Flush 房间（大巴等待室）”排队。
- **队长大包大揽**：当队列组建完毕，队长（Leader）站了出来。在进入 Flush 阶段时，队长不仅负责把全队的 `binlog` 写入内存缓存，他还顺手把全队刚才憋着没写的 `redo log`，**一次性打包（组写入）** 刷入了底层的物理磁盘！

结果：通过这个操作（把 redo log 的刷盘动作**后置**并合并），MySQL 5.7 终于实现了大一统： 在最严苛的“双 1 配置”下，原本 100 个并发事务需要经历 200 次惨烈的磁盘 I/O，现在经过 **redo log 组提交** 和 **binlog 组提交** 的双重压缩，直接被降维打击成了**区区几次 I/O**。

如果想提升 binlog 组提交的效果，可以通过设置下面这两个参数来实现：

- `binlog_group_commit_sync_delay= N`，表示在等待 N 微秒后直接调用 fsync，将处于文件系统中 page cache 中的 binlog 刷盘，也就是将「 binlog 文件」持久化到磁盘。

- `binlog_group_commit_sync_no_delay_count = N`，表示如果队列中的事务数达到 N 个，就忽视`binlog_group_commit_sync_delay `的设置，直接调用 fsync，将处于文件系统中 page cache 中的 binlog 刷盘。

如果在这一步完成后数据库崩溃，由于 binlog 中已经有了事务记录，MySQL会在重启后通过 redo log 刷盘的数据继续进行事务的提交。

## MySQL 磁盘 I/O 很高，有什么优化的方法？

给出了三招，本质上都是在**牺牲“数据的绝对安全性”来换取“极致的写入性能”**。

### 🟢 极低风险：【轻度拖延】组提交故意等待

- **调整参数**：`binlog_group_commit_sync_delay` 和 `binlog_group_commit_sync_no_delay_count`
- **通俗原理**：大巴车（组提交）到了收费站不立刻走，**故意原地等几毫秒**，硬凑够更多事务，然后一次性交过路费（合并刷盘）。
- **代价**：单条 SQL 的响应时间变长（因为在干等）。
- **严重程度**：🟢 **极低**。只要服务器本身没断电，单纯是 MySQL 软件（MySQL进程）崩溃，**不会**丢数据，因为数据已经交给了操作系统的内存 Page Cache。

### 🟡 中等风险：【中度拖延】批量刷 Binlog

- **调整参数**：`sync_binlog = N`（比如设置为 100 到 1000）
- **通俗原理**：打破每次提交必刷盘的规矩，现在**攒够 N 个事务**，才强行命令操作系统的内存 Page Cache真正去刷一次物理磁盘。
- **严重程度**：🟡 **中等**。如果主板断电，由于还有 N 个事务的 binlog 停留在操作系统内存里没下去，你会**永远失去这 N 个事务的归档日志**。

### 🔴 较高风险：【重度拖延】Redo Log 退守系统缓存

- **调整参数**：`innodb_flush_log_at_trx_commit = 2`
- **通俗原理**：打破“双 1”神话。每次事务提交时，底层的 redo log **只写到操作系统的内存（Page Cache）里就算完事**。至于什么时候真正刻进硬盘，全看操作系统的心情（通常系统自己是一秒刷一次）。
- **严重程度**：🔴 **较高**。同样， MySQL 软件（MySQL进程）崩溃，**不会**丢数据，；但一旦主机断电，你会**丢失最近这一小段时间（通常是 1 秒）内的所有真实数据更新**。



## 总结

具体更新一条记录` UPDATE t_user SET name ='xiaolin’WHERE id =1;`的流程如下：

- 1.执行器负责具体执行，会调用存储引擎的接口，通过主键索引树搜索获取id=1这一行记录：
  - 如果id=1这一行所在的数据页本来就在buffer pool 中，就直接返回给执行器更新
  - 如果记录不在buffer pool，将数据页从磁盘读入到buffer pool，返回记录给执行器。
- 2.执行器得到聚簇索引记录后，会看一下更新前的记录和更新后的记录是否一样：
  - 如果一样的话就不进行后续更新流程；
  - 如果不一样的话就把更新前的记录和更新后的记录都当作参数传给 InnoDB 层，让 InnoDB 真正的执0行更新记录的操作；
- 3.开启事务，InnoDB 层更新记录前，首先要记录相应的 undo log，因为这是更新操作，需要把被更新的列的旧值记下来，也就是要生成一条`undo log`，`undo log`会写入`Buffer Pool`中的Undo页面，不过在内存修改该Undo页面后，需要记录对应的`redo log`。
- 4.InnoDB 层开始更新记录，会先更新内存（同时标记为脏页），然后将记录写到`redo log`里面，这个时候更新就算完成了。为了减少磁盘I/O，不会立即将脏页写入磁盘，后续由后台线程选择一个合适的时机将脏页写入到磁盘。这就是 WAL 技术，MySQL的写操作并不是立刻写到磁盘上，而是先写redo日志到`Redo Log Buffer`，然后在合适的时间再将修改的行数据写到磁盘上。
- 5.至此，一条记录更新完了。
- 6.在一条更新语句执行完成后，然后开始记录该语句对应的 `binlog`，此时记录的`binlog`会被保存到` binlog cache`，并没有刷新到硬盘上的 `binlog `文件，在事务提交时才会统一将该事务运行过程中的所有 `binlog `刷新到硬盘。
- 7.事务提交（为了方便说明，这里不说组提交的过程，只说两阶段提交）：
  - prepare 阶段：将`redo log`对应的事务状态设置为`prepare`，然后将`redo log`刷新到硬盘
  - commit 阶段：将`binlog`刷新到磁盘，接着调用引擎的提交事务接口，将`redo log`状态设置为`commit`（将事务设置为`commit `状态后，刷入到磁盘`redo log`文件）
- 8.至此，一条更新语句执行完成。
